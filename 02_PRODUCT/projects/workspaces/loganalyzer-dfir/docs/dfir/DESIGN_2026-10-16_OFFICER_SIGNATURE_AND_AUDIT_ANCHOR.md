# Officer qualified signature and audit-log anchor (Standalone tamper evidence)

Date: 2026-10-16. Status: implemented, `TEST_VERIFIED` with software test certificates
(LogAnalyzer.Dfir.Tests `OfficerAndAnchorTests`, LogAnalyzer.App.Tests `OfficerQualifiedSignatureTests`,
`OfficerControlPageTests`). Signing with a real SafeNet card and acceptance by Adobe Reader are
`UNVERIFIED` until the manual steps at the end are run on a station. Background: owner decisions of
2026-10-16, `RESEARCH_2026-10-16_STANDARDS_STANDALONE_CLASSIFIED_WORKSTATIONS.md` sections 3-4 and
`PROVENANCE_2026-10-16_PDF_SIGNING_LIBRARIES.md` section 3.1.

## Problem

A local administrator can read the DPAPI-LocalMachine key that seals the head of the application's
audit log, rewrite the log and reseal it, and can re-sign a modified report with the station's report
key. Neither is detectable from the station alone.

## Design

1. **Only the officer's qualified signature makes a report official.** Every page of the report says
   "Fără semnătura electronică calificată a ofițerului de securitate acesta NU este raport oficial".
   There is no passphrase key file and no detached signature file: the signature is inside the PDF.
2. **Signing in the application.** "Semnează ca ofițer de securitate" lists the certificates on the
   inserted smart card (CurrentUser\My, key on the card, KeyUsage non-repudiation, valid now; the
   authentication certificate is not offered) and lets the officer pick one when there are several.
   A certificate that is not a trusted registered officer is refused. The PIN is asked by Windows /
   SafeNet; the application never sees the PIN or the key.
3. **PAdES B-B as one incremental update** (`PdfIncrementalSigner`, Core): the generated report
   (QuestPDF: PDF 1.4, classic xref table, uncompressed dictionaries) is left byte-for-byte as the
   prefix of a new `…_semnat_ofiter_<time>.pdf`; appended are the signature dictionary
   (`/Filter /Adobe.PPKLite /SubFilter /ETSI.CAdES.detached`, fixed-width `/ByteRange`, a 16 KiB
   `/Contents` placeholder, `/M` = claimed signing time), a signature field merged with a visible widget
   on the last page ("Semnat de <CN> - ofiter de securitate", date, issuer), the last page with
   `/Annots`, the catalog with `/AcroForm /SigFlags 3`, an xref section for only those objects and a
   trailer with `/Prev`. Cross-reference streams, object streams, existing forms or an already signed
   file are refused, not guessed.
4. **CMS** (`SignedCmsSigner`, App): `SignedCms` + `CmsSigner` from the WPF shared framework (no
   package), SHA-256, signer certificate only, signed attributes content-type, message-digest and ESS
   signing-certificate-v2 (RFC 5035, built with `AsnWriter`); no signing-time attribute.
5. **Verification** (`PdfSignatureCheck`, `OfficialReportVerifier`; the same for our output and for a
   file signed in Adobe): exactly one signature; `/ByteRange` starts at 0, covers the whole file except
   the `/Contents` hex string and nothing is appended after it ("modificat după semnare"); SubFilter
   `ETSI.CAdES.detached` or `adbe.pkcs7.detached`; the CMS verifies over the covered bytes; the
   original part (the prefix ending at one of the `%%EOF` before the signature update) has the SHA-256
   of a report the application generated, read from the sealed audit (`report.generated`), otherwise
   "raportul a fost modificat înainte de semnare"; the signer certificate has non-repudiation, was
   valid at `/M`, chains to a qualified CA certificate imported on the station and is not in an imported
   CRL that was in force at signing time (missing or expired CRL: "nu se poate confirma revocarea").
   Verdicts: **OFICIAL** only when all pass and the certificate fingerprint typed from the signed
   proces-verbal matches; **VALID, DAR NEOFICIAL** when it rests only on the station's officer list or
   the chain / revocation cannot be confirmed; **INVALID** with the reason. A non-INVALID verification
   appends `report.officer_signed` (cert fingerprint, CN, original and signed SHA-256, verdict) and the
   log is anchored again (`audit.anchor`), so the new code covers the signature event.
6. **Officer list** (`OfficerStore`, its own file under `%PROGRAMDATA%\LogAnalyzer\officers`, never part
   of the procedure profile; a profile import that carries officers or an anchor code is imported without
   them and audited as `profile.officer_import_ignored`). Officers are identified by the SHA-256 of their
   certificate (16 groups of 4 hex). The first officer is registered on trust and the fingerprint is
   shown to be written on the proces-verbal. Every later officer needs a registration request PDF
   generated by the application, which carries the new fingerprint in its original bytes and is signed
   by a registered officer (in the application or in Adobe); the signed request is kept and re-verified
   every time the list is read. Rows not reachable through valid approvals are not trusted. CA
   certificates and CRLs for the qualified signature are imported from files (`officer_trust.imported`).
7. **Anchor code** (`AuditAnchor`): 19 base32 characters of
   SHA-256("LogAnalyzer-audit-anchor-v1|chainId|seq|hash") + 1 check character, printed on the report and
   shown with a copy button; "Copiază jurnalul pentru CD-R" copies the log, its seal and `ancorare.txt`.
   At the next control the code is typed from the signed paper (the field is empty by default; the code
   the station remembers is shown only after an explicit click, labelled unsafe). Check **A11** says
   whether the code was typed or taken from the station.
8. **Checks**: A05 (1102, 104), A06 (4719, also CONFORM when none), A07 (4616), **A12** (Security 1100
   explained only by an actual shutdown: System 6006 within 5 minutes, or 1074 followed by a boot 6005;
   a cancelled shutdown explains nothing), **A13** (officer-list events in the sealed audit since the
   previous anchor, DE VERIFICAT).

## Security review of PR #289 (fixed, regression tests reproduce each probe)

- **Original vs. what follows it.** The original is the prefix whose SHA-256 equals a recorded report hash, and
  exactly one incremental update may follow it (`PdfUpdateInspector`): the signature dictionary, signature
  widgets (at most a quarter of a page), appearance streams and fonts, the AcroForm, the catalog changed only by
  `/AcroForm` (`/Perms`, `/DSS`, `/Metadata`, `/Extensions`), pages changed only by `/Annots` (new entries must be
  signature widgets) and the document information. A second update, compressed object streams, a replaced
  original object (content stream, font, page tree), another annotation or any action (`/JavaScript`,
  `/OpenAction`, `/AA`, `/Launch` …) gives INVALID "raportul a fost modificat înainte de semnare". Approval PDFs of
  officers follow the same rule, bound to the SHA-256 of the generated request.
- **Files changed outside the application.** Every officer / trust event and every `audit.anchor` carries
  `officer_state=store:<sha>,trust:<sha>,files:<names>` (SHA-256 of `security_officers.json` and of the
  `officer_trust` folder). A13 recomputes it; a difference from the last recorded state is NECONFORM
  "lista ofițerilor / autoritățile de încredere modificate în afara aplicației", with the files named. Officers
  from the station list are shown as "declarat pe stație (neconfirmat)"; only the paper fingerprint confirms.
- **Total parsing.** Malformed `/M`, odd-length or truncated `/Contents`, damaged structure and planted approval
  files give INVALID with a reason (or an untrusted row), never an exception.
- **Padding.** Everything after the DER CMS in `/Contents` must be `0`; otherwise INVALID.
- **"Calificată" only when declared.** The label is "semnătură electronică calificată" only when the certificate
  carries QcStatements with QcCompliance (0.4.0.1862.1.1) and QcSSCD (0.4.0.1862.1.4); otherwise "semnătură
  electronică avansată (certificatul nu declară că e calificat)". The verdict is unchanged.
- **Runtime.** Below .NET 10.0.13 every verdict carries "actualizați .NET la 10.0.13+ (remediere de securitate
  pentru verificarea semnăturilor)".
- **KeyGen.** `verify-report <signed.pdf> --officer-fingerprint <fp> --report-sha256 <sha> [--ca …] [--crl …]`
  runs the same verifier (the CMS source file is linked; KeyGen references the Microsoft
  `Microsoft.WindowsDesktop.App` shared framework, no package). Exit 0 OFICIAL, 5 valid but not official,
  2 INVALID, 1 usage.

## Security review of PR #289, round 2 (fixed, probes P7–P12 are regression tests)

- **Real parser instead of text search** (`PdfParser`, `PdfUpdateInspector`): the update after the generated
  report is tokenised (white space incl. NUL and form feed, comments between any tokens, names with `#xx`
  decoded, literal and hex strings, dictionaries, arrays, references, streams by their direct `/Length`). Its
  classic xref table is read: every in-use entry must point exactly at a parsed object, every object must have
  its entry, a FREE entry is refused (P8 comment inside an object header, P9 page content marked free).
- **Whitelist.** Original objects that may appear: only the catalog (identical, plus `/AcroForm`) and the one
  page that gets the widget (identical, plus `/Annots`), compared as parsed dictionaries. New objects must be
  reachable from `/AcroForm` or `/Annots` and keep to their role's keys: AcroForm {Fields, SigFlags, DR, DA};
  exactly one widget {Type, Subtype, FT, Rect, P, F, T, V, AP, DA, MK, Ff}, inside the page and at most a quarter
  of it; exactly one signature {Type, Filter, SubFilter, ByteRange, Contents, M, Name, Reason, Location,
  ContactInfo, Prop_Build}; form XObjects {Type, Subtype, BBox, Resources, Matrix, Length, Filter, FormType}
  with a scale/translate Matrix only; fonts and their descriptors, files and encodings. Anything else (actions
  even with escaped names `/Java#53cript`, `/J#53`, links `/URI`, `/XFA`, a second widget) is INVALID (P7, P10,
  P11).
- **A13 baseline from the paper** (P12): the state is the one recorded with the anchor whose code was TYPED
  from the proces-verbal; after it only an officer / trust event of the application may introduce a new state.
  A state that changes on an anchor or any other event, or differs now, is NECONFORM. Without a typed code A13
  is NEDETERMINAT.
- The certificate line uses the same "calificată / avansată" label; a signature dictionary ending with its hex
  `/Contents` is read correctly.

## Security review of PR #289, round 3 (fixed; the reviewer's overlay probe and the others are regression tests)

- **The signature place is reserved when the report is generated.** The report ends with a page of its own that
  holds only the heading "Semnătura ofițerului de securitate" and an empty framed box (`SignatureBoxPage`), and
  the generated file already contains an empty signature field `Semnatura ofiterului de securitate` whose widget
  covers exactly that box (`SignatureField.Reserve`, an incremental section appended before the report hash is
  recorded). The approval request PDFs for new officers are generated the same way.
- **Signing only fills that field.** Our signer and the inspector allow, after the generated file, exactly: the
  signature dictionary, the reserved widget with `/V` and `/AP` added (nothing else of it, Rect unchanged), the
  AcroForm with `/SigFlags`, `/DR`, `/DA` added, and new appearance form XObjects and fonts. The page and the
  catalog must not appear in the update; no new widget or annotation is possible.
- **The appearance stays in the box.** `/BBox` must have the size of the reserved box and `/Matrix` must be
  identity or absent; resources are fonts only; the content stream is decoded (none or FlateDecode) and may use
  only text and simple path operators (BT ET Tf Td TD Tm T* Tj TJ ' " Tc Tw Tz TL Ts g G rg RG k K re m l c h S s f
  F f* B B* b b* n q Q cm w W W*). Images (BI/ID/EI), XObject calls (Do) and graphics-state dictionaries (gs) are
  refused.
- **Exact xref grammar** for the update: "xref" end of line, subsection headers "N M", entries of exactly 20
  bytes "nnnnnnnnnn ggggg n|f" with SP CR, SP LF or CR LF, no comments, integers only; `/Root`, `/Info` must be
  generation 0 and `/Prev`, `/Size`, startxref integers.
- **Fonts:** font programs, ToUnicode and CIDToGIDMap streams only with no filter or FlateDecode, no /DecodeParms.
- **Provenance of the previous anchor code** is the action, not a value comparison: the field is empty; only the
  button "Folosește codul propus de stație (nesigur)" fills it with the station's suggestion and marks it; any
  edit by the officer clears the mark.
- **Supported signatures:** signed in LogAnalyzer, or in Adobe Acrobat/Reader **in the existing field**
  "Semnatura ofiterului de securitate" (Adobe: Tools → Certificates/Fill & Sign → click the field → choose the
  card certificate). A signature added in a new field drawn by hand, or with an image appearance, is INVALID.
- **CI:** the malformed-input tests now run each case on a dedicated thread (`TaskCreationOptions.LongRunning`):
  on the runner a thread-pool item could wait in the queue past the 15 s limit and be reported as a hang. The
  pcapng reader was checked and is bounded (every block advances the stream, every option loop advances, DNS
  name pointers are depth-limited); the exact CI case (last block cut inside its trailing length) has its own
  test that finishes at once and keeps every frame.

## Hardening after the round-4 review

- The signature appearance must START with the clip to its own box (`[q] 0 0 W H re W n`) and keep it in force
  to the end: the graphics-state depth after `W n` is the clip's level, no `Q` may go below it (an unbalanced `Q`
  is refused), except one `Q` that closes the leading `q` and must be the last operator. Our signer writes
  `q 0 0 W H re W n … Q`. Within those rules the appearance can only draw inside the reserved box (viewers also
  clip a form XObject to its BBox, which must equal the box); it can still draw anything there.
- Font programs, ToUnicode and CIDToGIDMap streams are decoded under a 4 MB limit (appearances 1 MB); beyond it,
  INVALID.
- Not done yet: the installation date in the anchored state (it depends on AppInstallDate, which is not in main).

## Verifying outside the application (OpenSSL)

The signature is a standard PAdES / CAdES detached signature. On a separate machine:

```
# 1. the ByteRange [a b c d] from the signature dictionary (text search in the PDF)
# 2. the signed bytes: everything except the /Contents hex string
head -c b report.pdf >  signed.bin ; tail -c +$((c+1)) report.pdf | head -c d >> signed.bin
# 3. the CMS: the hex between < > after /Contents, trailing zeros removed
xxd -r -p contents.hex > sig.p7s
openssl cms -verify -binary -inform DER -in sig.p7s -content signed.bin -CAfile qualified_ca.pem -crl_check -CRLfile issuer.crl -purpose any -out /dev/null
openssl pkcs7 -inform DER -in sig.p7s -print_certs | openssl x509 -noout -fingerprint -sha256
```

Compare the SHA-256 fingerprint with the one on the proces-verbal. Adobe Reader shows the same
signature in its Signatures panel.

## What a malicious administrator can still do

- Stop the application, kill Windows logging (no 1100 is written when the service is killed), change
  the OS before events are written; the anchor only proves the application's own log was not rewritten
  *before the anchored entry*, and only when the code is typed from the signed paper.
- Rewrite entries written *after* the last anchor (no external copy of those yet).
- Wipe the officer list and register a certificate of their own as "first officer": the app will then
  let that certificate sign and report "VALID, DAR NEOFICIAL"; OFICIAL still needs the fingerprint from
  the earlier signed paper, which will not match. A13 lists the registration.
- Generate a different report and record its hash (`report.generated` is written by the application
  under the administrator's session): the officer must read what they sign.
- Import a CA certificate of their own: the chain check then passes for certificates from that CA, but
  the fingerprint from paper still decides OFICIAL.
- The signature appearance draws only inside the box reserved on the last page of its own (round 3 below);
  that page holds no report content, so the appearance cannot cover any finding, anchor code or fingerprint.
- The whitelist is strict: if Adobe Reader writes extra keys or objects when signing (e.g. /Info or /Metadata
  updates, image appearances), an Adobe-signed report is INVALID until the whitelist is widened after the
  manual Adobe test. Our own signature passes.
- A13 trusts the officer / trust events that the application wrote in its sealed log. A11 covers the log only
  up to the anchored entry: an administrator with the machine key can append (or rewrite) entries AFTER the
  paper anchor, including officer / trust events that make a hand-made change look legitimate. Such events are
  not NECONFORM; they appear in A13 as changes made through the application (DE VERIFICAT), which the officer
  must confirm against the signed proces-verbal. Neither A11 nor A13 detects them by itself.
- The report hashes that make an "original" acceptable are recorded on the station (`report.generated`, sealed
  with the machine key): they do not stop a station administrator from recording a report of their own.
  Off the station, `verify-report --report-sha256` is only as good as where that hash comes from (it should be
  copied from the signed proces-verbal, not from the station).
- A certificate revoked after signing makes older signatures fail too (the imported CRL parser keeps
  serial numbers, not revocation dates): conservative.
- Without a timestamp authority the signing time `/M` is only claimed (PAdES B-B).

## Manual test with a real SafeNet card and Adobe Reader (to do on a station)

1. Station runtime `Microsoft.WindowsDesktop.App` 10.0.13 or later (CVE-2026-84008 in SignedCms).
2. Insert the officer's card; check in `certmgr.msc` → Personal that the qualified certificate is there
   with "You have a private key" and Key Usage "Non-Repudiation".
3. Import the QTSP CA certificate(s) and CRL with "Importă autorități de certificare și liste de revocare…".
4. "Ofițeri de securitate…" → Yes (card) → write the shown fingerprint on the proces-verbal.
5. Run a control, then "Semnează ca ofițer de securitate": the SafeNet PIN dialog must appear; the
   signed file opens. Expected verdict: VALID, DAR NEOFICIAL (no paper fingerprint yet).
6. "Verifică raport semnat…" with the fingerprint typed from the proces-verbal: expected OFICIAL.
7. Open the signed file in Adobe Reader: Signatures panel must show the signature as valid, the
   document as unmodified since signing, and the certificate chain (Adobe trust list permitting).
8. In Adobe, sign a copy of an unsigned report with the same card, IN THE EXISTING FIELD "Semnatura
   ofiterului de securitate", and verify it in the application: expected the same verdicts. If Adobe adds
   objects the whitelist does not know, the verdict is INVALID with the reason: report it, the whitelist is
   widened only after review. Then add a comment in Adobe after signing and verify: expected INVALID
   "modificat după semnare".
