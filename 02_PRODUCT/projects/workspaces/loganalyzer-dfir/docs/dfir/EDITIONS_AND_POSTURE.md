# Editions and station posture

One codebase builds three executables. The posture of the station each one is made for is fixed at compile time.

| Edition | Executable | Posture | Window and report label |
|---|---|---|---|
| Standalone (air-gapped station, no network, no internet) | `LogAnalyzer.Standalone.exe` | `StationPosture.Standalone` | Ediția: Standalone |
| Network (air-gapped LAN: domain controllers, servers, domains; no internet) | `LogAnalyzer.Retea.exe` | `StationPosture.IsolatedNetwork` | Ediția: Rețea air-gap |
| Internet (everything) | `LogAnalyzer.Internet.exe` | `StationPosture.Internet` | Ediția: Internet |

## What each edition contains

- **Standalone** references only Core, Infrastructure and Dfir.Windows. It contains no network code: no sockets, HTTP, directory (LDAP) access, syslog, live event watchers, response actions or AI. `LogAnalyzer.Edition.Tests` scans the build output to keep it that way.
- **Network** adds `LogAnalyzer.Connectors` (read-only domain collection, syslog and internal SIEM forwarding, live event watchers) and `LogAnalyzer.Response` (CSIRT actions). It does not contain `LogAnalyzer.Ai` (the AI layer, which uses an HTTP client) unless the build option `-p:NetworkIncludeLocalAi=true` is used (owner approval required; loopback only). It contains no cloud client and no online downloader or updater; the edition test bans HTTP/web clients outside `LogAnalyzer.Connectors`.
- **Internet** is the complete application (`LogAnalyzer.App`).

## Posture and the signed edition policy

The compile-time posture always wins. It is chosen by the edition's composition, never by a file, an argument or a policy. A signed policy can only choose the runtime mode (`AppMode`) inside what the posture permits (`StationPostures.ClampMode`): a Standalone edition is always AirGapped; a Network edition may be narrowed to AirGapped by a policy but never widened beyond the LAN; the Internet edition follows the policy. No policy can widen the posture.

## Owner decisions on the editions

- **Wrong-edition warning (Internet edition).** When the Internet edition runs on a station that looks isolated, Home and the control report header show: "Ediție nepotrivită: stația pare izolată. Pentru o stație fără rețea folosiți LogAnalyzer.Standalone, pentru o rețea internă fără internet LogAnalyzer.Retea." The test reuses the passive N11 facts: the station looks isolated when it has no ACTIVE way out of any kind (no gateway or DNS server on an adapter that is up, no active proxy, VPN, tunnel, radio or cellular modem). An internal gateway counts as a way out (a NAT router behind it may reach the internet), so a connected office station behind NAT is not warned. When a source cannot be read, nothing is guessed and no warning is shown. The warning never changes a check result.
- **Local AI in the Network edition** stays OUT of the default build. The opt-in build option `-p:NetworkIncludeLocalAi=true` is unchanged (owner approval, loopback only); the edition test proves the default output has no `LogAnalyzer.Ai`.
- **Removable media on the Internet edition.** Data leakage through USB sticks is a risk on every station, so P14 (USB storage blocked by policy), A08 (copies to removable media audited) and D02 (BitLocker To Go on removable media) apply to the Internet edition too; D01 (USB connection history) already did. The printing log (P29), CD/DVD burning (P28) and the classification banner (P26) stay "NU SE APLICĂ" there.
- **Active domain-controller check N13 (Network edition only).** Only on a domain-joined station (N12) and only when the network gate allows traffic (`NetworkPolicy`). Locating the domain controller uses Windows' normal domain-locator traffic, the same as at every domain logon: `DsGetDcName` (Netlogon) queries the CONFIGURED DNS server for the SRV record `_ldap._tcp.dc._msdcs.<domain>` and pings the candidate controllers over UDP 389, and the controller's name is resolved through the same DNS server. That traffic leaves before any address is known, so it is not filtered by address. The probe's own traffic is a single TCP connection to LDAP (389), opened only to a PRIVATE address (RFC 1918 or fc00::/7), without credentials and without sending data. Loopback and link-local addresses never receive it. If any resolved address is public, the probe opens no TCP connection and N13 is non-conform ("controlerul de domeniu se rezolvă la o adresă publică"). The whole probe (locator, name resolution, connection) has one 10-second deadline; a stalled locator or DNS server is abandoned and reported for review ("controlerul de domeniu nu a răspuns în … s"), a cancelled run is NEDETERMINAT. The detail names the DC address given by the locator and the configured DNS servers when known. The probe lives in `LogAnalyzer.Connectors`, which the Standalone edition does not contain; the Standalone build test bans its type by name. N13 does not apply to Standalone or Internet.
- **Officer-signed media register (2026-10-16, check D04).** All storage media are inserted at once on the transfer station and enrolled ("Medii de stocare" → "Registrul semnat" → "Înrolează mediile conectate"): USB serial, VID/PID, vendor and model, capacity, volume serial, BitLocker To Go state and persistent volume id are read from the station; the operator fills in inventory number, classification level and holder (HG 585/2002 art. 294); an unencrypted medium is warned about (BitLocker To Go recommended). The register is canonical JSON (keys sorted, no whitespace, UTF-8 without BOM) with `version`, `previous_version_sha256`, `station_id`, `issued_utc` and `entries`, signed by the security officer's qualified card certificate as a detached CMS (`.p7s`, SignedCms, the same signer as the report signature; no passphrase files) and exported for transport. Every station imports it: the CMS must verify over the exact bytes, the signer must be a trusted officer of the station, the certificate must chain to an imported qualified CA and not be revoked in an imported CRL, and the fingerprint typed from the proces-verbal must match; only then is it OFICIAL. Without the paper fingerprint (or with an unconfirmed chain) it is NEOFICIAL, kept in the history and never used for compliance. An OFICIAL version is installed only when its version is higher than the installed one and its `previous_version_sha256` is the installed one's hash (anti-rollback); the outcome is written to the sealed audit first (`media_register.imported` / `media_register.refused`), and a version is installed only when that entry was written. At every control the installed file is re-hashed, its signature re-verified against the fingerprint confirmed at import, and its version compared with the last install in the sealed audit (an older file put back by hand or a deleted state is NECONFORM). D04 compares every removable medium the station has seen (connected now and history) with the active register by serial, VID/PID, capacity (relative tolerance, default 2 %, a station setting `capacity_tolerance` in `%APPDATA%\LogAnalyzer\media_matching.json`, accepted 0 to 0.10, out of range gives the default and a warning in D04; the default is not lab-verified, so "de verificat în laborator" with real media) and BitLocker volume id when both sides have it: not in the register, or retired / destroyed and seen after that date = NECONFORM; same serial with different attributes = "posibilă clonare a serialului" (DE VERIFICAT). An unregistered medium seen only before the first OFICIAL installation recorded in the sealed audit (on Standalone without that date: before the application's install date) and not connected now is "istoric dinaintea registrului semnat" (DE VERIFICAT); seen after it, connected now or with no known time it stays NECONFORM. The control report's officer section prints the installed register's version and SHA-256 next to the anchor code; a station left on an older version is detected only by comparing the proces-verbale of the stations. The live transfer register uses the same register: an exit on a medium whose serial (or inventory number) is not an active medium of the signed register cannot be approved ("mediul nu este în registrul semnat"); with no register in force, no exit on a medium is approved; a registered serial seen on the station with other attributes cannot approve either ("mediul observat nu corespunde înregistrării din registru (posibilă clonare)"). Limits: a medium without a unique serial cannot be enrolled or recognised; attributes can be forged by purpose-built hardware, which is why several are compared; the offline case analysis uses a signed media register found in the case folder only after the same checks as the live path (CMS signature, trusted officer, qualified chain, paper fingerprint confirmed on the analysing station); an invalid one is not used and the reason is shown, and a case without one is unchanged; D04 does not apply to the Internet edition.
- **Real-time device monitor replaces the media register in the interface (2026-10-16, check D05).** The officer-signed media register above is switched off by one flag (`MediaRegisterFeature`, default off): its tabs and the register columns are hidden, D04 is "Nu se aplică" with the reason "registrul semnat al mediilor nu este folosit pe această stație", the transfer register does not require it; the code and its tests stay. The media page (menu "Monitor dispozitive") opens on "Monitor în timp real", which lists ONLY storage media and externally connected devices (stick, memory card, external disk, optical drive, phone / tablet over MTP, PTP or ADB, camera, scanner, printer, USB network / Wi-Fi / modem adapter, Bluetooth device, external keyboard and mouse, smart card reader, card reader with the inserted card as its own row). Hubs, host controllers, composite parents, HID child collections, software and virtual devices, ACPI and system devices, internal disks, integrated readers, the Bluetooth radio itself and integrated webcams, keyboards and touchpads are out of scope. One pure classifier (`DeviceScope`) decides the scope for the page, check D05 and report section 3c alike: the container id of the device (DEVPKEY_Device_ContainerId / InLocalMachineContainer) tells internal from external and groups the nodes of one physical device into one row; disks use the bus (USB, SD, MMC). The list is read through SetupAPI with the Configuration Manager problem code (28 = no driver, 22 = disabled) and diffed by PnP id on every WMI device event, or every 2 seconds when the events are unavailable. There are no driver columns: the status word is Conectat, Deconectat, "Nu funcționează (fără driver)" or Dezactivat. Each row has a green (connected) or red (disconnected) circle, type, name, manufacturer, model, VID/PID, serial ("fără serie unică" when Windows made it up), for media capacity, letter and label, the account of the active console session at the connection (WTS; "—" when nobody was logged on), first seen / last connected / last disconnected (local and UTC), an editable registration number keyed by the device identity (serial + VID/PID when the serial is unique, otherwise the instance id; a card by volume serial + capacity) and the alert. Every edit is written to the sealed audit first (`device.registration_number_changed`: old and new value, operator, time) and refused when it cannot be. A serial that comes back with another capacity or manufacturer is a separate row marked "serie duplicată – posibilă clonă" with a critical alert, like two present devices with the same serial. Rows persist in `%ProgramData%\LogAnalyzer\device_monitor\device_monitor.json` (machine-wide; folder created with an explicit ACL: SYSTEM and Administrators full control, Authenticated Users modify on the file only; an owner other than SYSTEM or Administrators makes the journal untrusted and the sealed audit wins; the old `%APPDATA%` journal is moved once and the move is sealed). The monitor seals its own start, a heartbeat every 15 minutes and its stop (`device.monitor_started`, `device.monitor_heartbeat`, `device.monitor_stopped`), the intervals it lost (`device.monitor_gap`: watcher error, overflow, WMI service stop, station asleep) and, after a gap, a full rescan (`device.observed_on_resume`). A connection raises the window banner: critical (red, sound) for a storage medium without a registration number on every posture, for a possible clone and, on Standalone and the isolated LAN, for phones, Bluetooth, Wi-Fi, modem and USB network adapters; information otherwise. Pop-ups are rate limited (per device and alert kind once per 10 minutes, 20 per minute overall, with an "N alerte suprimate" counter) but every alert is journaled and sealed (`device.alert_critical`, `device.alert_info`). A Bluetooth radio that is off or absent or a disabled Wi-Fi adapter is reported as such, never as "no devices". D05 (report section 3c) lists the in-scope devices seen in the period and the alerts, and judges: coverage is computed ONLY from the sealed running windows (none over the period: NEDETERMINAT; partial: DE VERIFICAT with each gap; CONFORM needs the whole period), the journal's own runs are a cross-check (a window the audit does not back is a tampering finding), registration numbers against the sealed audit (a deleted row is detected too), and the policy (NECONFORM on an isolated posture, DE VERIFICAT on Internet, when a storage medium has no number, a forbidden class was seen or a serial is duplicated); a critical alert that only the journal holds keeps it from CONFORM. Observe and alert only: nothing is blocked or changed. Limits: the monitor sees only while the application runs; times are when it observed the change; a device without a unique serial is recognised by its port; the Bluetooth switch of Windows Settings (a software radio toggle) is not visible, only an adapter disabled in Windows.
- **Device monitor page: columns, history, CSV, sealing rights (check D05, report section 3c).** The page lists the same kind of data as a device-control console and nothing else: Stare (green/red circle plus the status word Conectat / Deconectat / Nu funcționează (fără driver) / Dezactivat), Nume, Tip, Producător, Model, VID, PID, Serie, Capacitate, Literă, Etichetă (the last three for storage media only; storage media are never merged or shown as another class), Utilizator (console account at connection), Prima apariție, Ultima conectare, Ultima deconectare (local time dd.MM.yyyy HH:mm:ss), Nr. de înregistrare (edited through the sealed-audit path), Registru (Înregistrat / Neînregistrat) and Alertă; no driver columns. Default order: connected first, then last connection descending; every column sorts (dates by their real value). "Istoric" (row action) lists that device's SEALED events from the operation audit (`DeviceHistory`, pure, in `LogAnalyzer.Dfir.Devices`): first seen, connection, disconnection, registration number change (old → new, operator), alerts, state changes; records whose write was refused are shown last, marked "în așteptare (nesigilat)". "Export CSV" writes the rows in view (current sort) as UTF-8 with BOM, ';' separated (`DeviceCsv`, formula-leading values prefixed with an apostrophe), then seals `device.export_csv` (operator, rows, SHA-256 of the file, never the path); if the audit refuses the note the file is removed again. Sealing rights: when the audit refuses a record because its sealing key cannot be read (the application was not started as administrator; recognised by `SealingHealth.KeyUnavailableMarker`, kept in step with the real `HashChain` message by a test) the page shows a persistent red banner and the journal records the first and last refusal (`sealing_refused`, untrusted like the rest of the journal); D05 lists "MONITORUL A RULAT FĂRĂ DREPT DE SIGILARE" and cannot be CONFORM for a period it overlaps. The manifest and elevation are unchanged. Section 3c prints the same fields per device (`DeviceMonitorReport.Line`) over the same `DeviceScope` predicate.
- **Media history across stations (2026-10-16, every edition).** After a control, "Exportă istoricul mediilor pentru ofițer" (control page) builds the station's history of removable media as canonical JSON (format `loganalyzer.media_history.v1`, the same canonical rules as the signed media register): the station's Hardware ID and computer name, edition and posture, Windows time zone, export time, the sealed-audit anchor code and sequence at export, the version and SHA-256 of the signed media register in force, and for every removable medium (connected now and history) serial, VID/PID, capacity, BitLocker volume id, volume serials, drive letters, first and last connection, every connection window known (Windows logs every arrival but only the last removal, so only the last window has an end), and the file activity on it found by A15 (written to the medium, named in a copy or archive command, opened from it: file name, SHA-256 when known, time, direction); activity on a removable drive that names no serial is kept apart as unattributed. It also carries the station's transfer-register rows that involve a medium and the SHA-256 of the classified files present. The security officer, physically present, signs it with the qualified card certificate (detached CMS `.p7s`, SignedCms; the station operator needs no card); `media_history.exported` with the export's SHA-256 is written to the sealed audit first and the files are written to the officer's medium only when that entry was written. No network code is involved: the transport is the officer's removable medium. On the officer's station, "Medii de stocare" → "Confruntare între stații" imports the exports: each is refused unless canonical, its CMS verifies over the exact bytes, the signer is on that station's officer list (pinned by certificate fingerprint) and the certificate chains to an imported qualified CA and is not revoked in an imported CRL (fail closed: an unconfirmed chain is refused). Each export's register version is compared with the latest signed register installed on the officer's station ("registru învechit"). For every approved transfer row (time, approval, medium serial or inventory number, source and/or destination station) in the period, the reconciliation checks that the medium was connected at the source within ±2 h of the register time (typed in the station's declared time zone), at the destination within 72 h after it, and that every SHA-256 of the row is on the destination (present classified files or file activity there). Every connection of the medium on any OTHER station that no approved row and no enrolment explains is listed ("mediul a fost introdus și în stația X") with the file activity known there: GRAV during a transfer or with file activity, RIDICAT otherwise; the transfer's own files (by SHA-256) found on such a station are a separate GRAV line. Media seen on any station but absent from the signed register are listed; the same serial on two stations closer in time than the minimum move time (default 10 minutes, configurable) or with attributes different from the register entry is "posibilă clonare a serialului". Stations named in the transfer rows (or listed as expected) without an accepted export are NEDETERMINAT. The result is a table sorted by severity and a report PDF with the reserved officer signature field, signed with the card in one click (`report.generated` then `media_history.reconciled` in the sealed audit) plus a CSV of the table. After review: every station's copy of a transfer row is grouped by transfer number; copies that differ in route, medium, time, direction or files are "înregistrări contradictorii pentru transferul X între stațiile A și B" (GRAV, both versions listed), and the row held by the SOURCE station named in it is the one evaluated (otherwise the row of the first station by identifier, flagged for checking on the paper register), so the result does not depend on the order in which the exports are loaded. Each export carries the station's tamper indicators at export time (A05 log clears 104/1102, A11 anchor continuity, A12 event log service stop, A13 officer list, A16 install date, S05 clock), each with the control's word; a check that did not run is "lipsă". Any indicator that is not CONFORM (or NU SE APLICĂ), or is missing, is a finding for that station ("istoricul acestei stații poate fi incomplet: …"; RIDICAT when one is NECONFORM, otherwise DE VERIFICAT), and every "transfer confirmat" line states for the source and destination stations whether their indicators are clean. The officer may type the anchor code from each station's proces-verbal ("STAȚIE = COD"); a code that differs from the export's is GRAV, an invalid code is DE VERIFICAT, a station without a typed code is named in the limits; a typed line whose station name or Hardware ID matches no accepted export is "cod de pe procesul-verbal pentru o stație necunoscută: <nume> (verificați numele)" (DE VERIFICAT). Residual limit, printed in every report: "indicatorii de integritate sunt calculați de stația verificată însăși, la export; un administrator care oprește serviciul de jurnale și șterge înregistrări individuale poate lăsa indicatorii curați; codul de ancorare tastat de pe procesul-verbal dovedește doar că jurnalul aplicației nu a fost rescris, nu că istoricul dispozitivelor din Windows este complet". An expected station whose export predates the end of the period is "export învechit" (DE VERIFICAT). A refused export is shown by file name, and any station name read from it is marked "(nume din fișier neverificat)". A clone suspicion based on timing is RIDICAT only when S05 is CONFORM on both stations; otherwise it is DE VERIFICAT with the clock state named. The source window (±2 h) and the destination window (from 2 h before to 72 h after) include their ends. Limits stated in every report: "un administrator poate șterge istoricul dispozitivelor unei stații; ștergerea lasă de regulă urme (104/1102, A11) raportate mai sus", stations that did not export, exports older than the end of the period, histories starting after the period start, media without a unique serial, stations without file auditing (A14), file activity not attributable to one medium, register times typed by hand, and the fact that a USB serial can be copied.
- **Default mode of the Internet edition without a signed policy:** still AirGapped. Changing it to the connected mode changes the signed-policy gate of the application and is left to the owner in the main session (not done here).

## Control check applicability

The audit result type has a fifth state, `NuSeAplica` ("Nu se aplică"). A check that does not apply to the posture is shown as such in the screen and the reports and is never counted as non-compliant (nor as compliant). The table is `ControlApplicability` in `LogAnalyzer.Dfir.Windows/Audit/ControlApplicability.cs`; a test keeps this document and the code equal and fails if the evaluator produces a check id without an entry for all three postures. There is no default.

Check families: C accounts, P policies, A audit, U users, D devices, N network, S software. "Review" means the application shows the facts and the organisation decides. "non-conform" means the finding is a violation in that posture.

Applicable checks: Standalone 81, IsolatedNetwork 81, Internet 62 (of 82).

Network checks N11 and N12 are specific to this model. N11 ("no path to the internet") is PASSIVE in every edition that runs it: it reads adapter properties, the registry (interface gateways and DNS servers including adapters that are off now, persistent routes, WinINet and WinHTTP proxy settings), the VPN/RAS phonebooks, the Plug and Play device list (cellular modems, phones used as modems), the count of saved Wi-Fi profile files and the Internet Connection Sharing state (HNetCfg COM object). It uses no WMI. It opens no socket and resolves no name, so a proxy given by name is shown as "review". A source that cannot be read is never taken as "nothing there": a phonebook or the Wi-Fi profile folder counts as absent only when it is confirmed missing from a folder that could be listed (File.Exists and Directory.Exists also answer "no" on access denied), and any unread source (adapters, interface registry and routes, proxies, VPN phonebooks, saved Wi-Fi profiles, ICS state, the adapter list behind cellular and phone modems) makes N11 NEDETERMINAT, with the source and the reason named in the detail. A path actually found still makes it non-conform; an ICS state that cannot be read while policy forbids ICS is "review", as in N10. On Standalone any such path is non-conform; on the Network edition internal gateways and DNS are accepted and a path leading outside the internal ranges is non-conform. Internal DNS answers are not checked passively. Domain controller reachability is checked ACTIVELY by N13, in the Network edition only (see below).

## Application installation date: residual risk

On a Standalone station every network connection after the installation of the application is NECONFORM, so the installation date is a boundary that an
administrator could try to move later. What the application does (`AppInstallDate`, `AppInstallTraces`):

- The first start is written into the application's audit chain (`app.first_start`) before licence activation, so a normal deployment (start, read the
  Hardware ID, wait for the licence, configure) keeps its first run inside the chain.
- The date is valid only if the whole chain verifies and starts with a store-creation record. It is the EARLIEST of the chain and of the traces of the
  INSTALLED edition executable: the application's own files, Prefetch (creation and run times), Amcache (last-write time of its entry, not a first
  sighting) and the oldest retained Security 4688 start.
- NECONFORM: a sealed store reinitialisation after a primary administrator existed, a repeated administrator creation, a broken chain, and a Windows RUN
  trace (Prefetch, 4688) of the installed executable before the chain began (history lost).
- DE VERIFICAT: earlier file or Amcache times of the installed executable; a run of an edition executable from another folder ("aplicația a rulat și din
  altă locație"); an Amcache entry of an edition executable at another path ("aplicația a existat/rulat anterior în altă locație", with path and last-write
  time); a newer Prefetch trace, i.e. a .pf of the installed executable created long after an older Windows trace of the same installed path (its Amcache
  entry or a Security 4688 start: "urmă Prefetch mai nouă decât alte urme Windows — poate fi recreată de Windows sau ștearsă", since Windows itself evicts
  and recreates the .pf of a rarely run program); a missing .pf while Prefetch is active ("posibilă ștergere"); and the absence of every Windows trace.
- The computed date and the time of the chain's first record are printed in every control report header, so two controls can be compared.

### Probe B (what an administrator can still achieve)

The administrator recreates the authentication store, reinstalls the application in a new folder and deletes the old .pf (Prefetch on, other .pf present):

- Achieved: the computed installation date moves later (to the reinstall), and no NECONFORM is raised by the station alone, because no remaining Windows
  trace proves a RUN before the new chain.
- Notes that remain (DE VERIFICAT): the old-folder Amcache entry ("existed/ran earlier in another location", reported with path and time) as long as
  Windows keeps it. The newer Prefetch trace note does not appear: it compares the new .pf only with older traces of the same installed path, and the
  new folder has none.
- Notes that disappear: "posibilă ștergere" (the new .pf hides it after the next run), and every note once Amcache drops or rewrites the old entry;
  with Prefetch off and Amcache unreadable only the "urmele Windows lipsesc" note is left.

The strong control is therefore the paper anchor: PR #289 (merged) anchors the station state on paper. The anchored state now also holds the installation
date (UTC and its basis) and the identity of the application's audit chain (its first record: hash, time, kind). It is written as the
`audit.anchor_state` entry immediately before the anchor is taken, so that entry IS the anchored one and the paper code covers its content; the report
prints the values read back from that entry next to the anchor code, to be copied onto the proces-verbal. If the entry cannot be written, no anchor
code is issued.

At the next control, check A16 compares with the anchored state of the code typed from the paper:

- the audit chain identity decides incidents: another first record means the chain was reinitialised after the previous control, NECONFORM
  ("jurnalul aplicației a fost reinițializat după controlul anterior (identitatea jurnalului s-a schimbat)");
- the installation date computed from traces is informative only. It legitimately moves LATER after an update of the application (program files
  recreated), an eviction of Prefetch traces, or a control run under another Windows account (other LocalAppData traces), so a later date, a date that can
  no longer be computed, or an earlier one (an older trace found) is DE VERIFICAT, to be confirmed from the proces-verbal; within one day it is the same;
- without a typed code, or with an anchor that has no anchored state, A16 is NEDETERMINAT.

Probe B (reinitialised store) therefore becomes visible at the first control after it, provided the officer types the code from the paper. It is A11 that
catches a reinitialisation: the new chain no longer contains the paper code, so A11 is NECONFORM, and A16 (which needs the anchored entry of that code) shows
NEDETERMINAT "nu se poate compara: jurnalul nu mai conține codul de pe procesul-verbal (vezi A11)". A16's chain-identity check is defence in depth for the
case where the anchored entry is still found. What remains: a reinstall BEFORE the first anchored control is not
caught; an administrator who rewrites the anchored state entry (with the machine key) is caught by A11, because the code typed from the paper no longer
matches.

## The application's own commands (A17): recognition and residual risk

Owner rule 2026-10-16: the programs the application itself starts to read logs, the registry, shadow copies, the audit policy or to hash files only
check existence, absence and correlation of data; they must never be reported as abuse. Recognition never uses folder or file names (a name-based
exclusion was removed earlier because an attacker can imitate it).

Inventory of what the application starts (`CollectorExec.Start` is the only path; each start writes `collector.exec` to the sealed audit before it
starts and `collector.exec_done` after it ends):

| Caller | Program | What it reads or does | Rules it could trigger |
|---|---|---|---|
| `ToolRunner` (acquisition) | `reg.exe save`, `esentutl.exe /y /vss`, `bcdedit.exe /enum` | registry hives, SRUM / Amcache through a shadow copy, boot configuration | 4688 command-line rules, VSS rules, LOLBin / EXEC rules |
| `PowerShellAuditCollector` (Unclassified, Network) | `powershell.exe -File Scripts\AuditCollector.ps1` (script SHA-256 recorded) | the bundled collection script | 4104 script-block rules (U06), 4688 |
| `AuditPolicyChange` (Unclassified) | `auditpol.exe /set` | enables one audit subcategory after the operator agrees | 4688, audit-policy change (A06, the change itself stays reported) |
| `NetshRunner` (Unclassified, Network) | `netsh.exe advfirewall` | firewall isolation rules started by the operator | 4688 |
| `ProcessScanner` (containment) | `MpCmdRun.exe -Scan` | Defender scan of one file | 4688 |

Not recorded: files and folders the operator opens from the interface (`UseShellExecute`, a report or `explorer.exe` on a folder). They are viewers
the operator starts by hand, not collection, and their events stay ordinary events. Event logs are read through `EvtExportLog` / `EventLogReader`
and WMI queries in-process: they start no program.

An event (Security 4688, Sysmon 1, PowerShell 4104) is the application's own only when it matches a record that passes the same run validation as a
hashing window (chain verifies, no backdated record before it, named control run with start and end, inside it, written by the executable recorded at
the control start, the control starts after the anchor before it) and moreover: the application's process id, the program's full path and SHA-256, the end
record (child process id, exit code), at most 10 minutes; the program must be one of the fixed inventory (System32 `reg.exe`, `esentutl.exe`,
`bcdedit.exe`, `auditpol.exe`, resolved from `Environment.SystemDirectory`, and Defender's `MpCmdRun.exe` under Program Files or, only at exactly `%ProgramData%\Microsoft\Windows Defender\Platform\<version>\MpCmdRun.exe` (version `^\d+(\.\d+){3}(-\d+)?$`, case-insensitive, canonical path: no `..`, no extra segment, no UNC, no alternate data stream, no other parent), the platform copy the stub starts; normalised,
case-insensitive; the Unclassified and Network compositions add System32 `netsh.exe` and `WindowsPowerShell\v1.0\powershell.exe`, because only they
ship the firewall runner and the collection script, so the Standalone build contains neither). A PowerShell record is accepted only when its command
line is exactly the one the collector emits (the fixed switches, `-File` with the shipped script path, one of the target types, an output folder and a
host name the collector accepts, nothing else) and its recorded script hash is the hash of the script embedded at build time; any other PowerShell command line is refused. For every program, the file
at that path must hash now to the recorded SHA-256. A record naming
any other program (for example `C:\Tools\exfil.exe`) is refused. The collection script is started only when its SHA-256 equals the hash of the
script embedded in the assembly at build time; a changed script is refused before anything starts. The event must have the same child process id (or the application's process as parent)
inside that window, the same path and the same command line, and, when it carries one (Sysmon), the same image hash; a script block must have the
recorded script hash. Matched events leave every other check and are listed by A17 ("Activitate proprie a aplicației: N comenzi, toate consemnate");
look-alikes stay ordinary events; an event that matches only a refused record is "activitate pretinsă a aplicației, neconfirmată" (A17 DE VERIFICAT)
and stays with the other checks.

Commands started outside a station control (investigation, containment) get an action window of their own in the sealed audit: `action.started` with a run id
(`act-` + the execution id the application wrote itself) and the application hash before `collector.exec`, `action.finished` after `collector.exec_done`. The same
validation then confirms them. A run id cannot be forged from a process name or a command line: the window must exist in the sealed audit and cover exactly that command.

Residual: an administrator who holds the sealing key can append, after the latest anchor code, forged records for the programs of the application's
inventory and so hide any number of runs of those programs at the next control. A11 does not detect entries appended after the anchor (it proves only
that what the paper code covers is unchanged). The officer compares the A17 list with what the application's operator actually ran. The inventory and
the current-hash check limit what can be hidden to runs of those Windows tools with their own files; they do not limit how many. Between the check of
the script's hash and PowerShell reading the script there is a short window in which an administrator who can write to the application folder can
replace the script; with script block logging (4104) on, the replaced content shows as not matching; without it, only the PowerShell start is seen, and
it is recognised as the application's own. A long PowerShell
script that Windows splits into several 4104 events (same ScriptBlockId, MessageNumber of MessageTotal) is reassembled in order before the hash is compared; a set that
is incomplete or has a duplicated number is never confirmed and stays A17 DE VERIFICAT with the reason, and parts of different ScriptBlockIds are never merged.
