# XAU_Kinetic Clean Architecture Principles

## Overview
`XAU_Kinetic` is a institutional quantitative trading engine built with Clean Architecture in Python 3.12+. It separates concerns strictly between core domain entities, application orchestration, infrastructure drivers, risk management, and trading strategy decisions.

```text
xau_kinetic/
├── domain/                  # Pydantic V2 immutable data entities
├── application/             # Clean Abstract Base Classes & StrategyRunner orchestrator
├── infrastructure/          # MT5 client wrapper & SQLite WAL SHA-256 persistence
├── risk/                    # Isolated circuit breaker & exposure manager (VETO authority)
├── strategies/              # Pure functional strategy logic (closed bar evaluation)
└── main.py                  # Dependency injection & execution entry point
```

## Core Architectural Invariants

### 1. Zero-Trust Data Flow (Pydantic V2)
All inputs and outputs crossing architectural boundaries use strict Pydantic V2 schemas (`SignalObject`, `Position`, `TickData`, `AccountInfo`, `OrderResult`, `AuditEvent`). No raw dictionaries or unvalidated floating point values are passed between strategy and risk modules.

### 2. Isolated Risk Veto Power
`RiskManager` acts as an independent circuit breaker and position sizing engine. It has absolute VETO authority over signals generated by strategies. A strategy cannot bypass or modify risk parameters (max daily drawdown %, max symbol exposure lots, min free margin).

### 3. Anti-Look-Ahead Execution
To prevent look-ahead bias during live execution and backtesting, strategy indicator calculations evaluate completed closed candles ONLY (`df.iloc[-2]`). Unclosed current candles (`df.iloc[-1]`) are forbidden from triggering trading decisions.

### 4. Multi-TP Ladder & Break-Even Risk Elimination
Positions can scale out across multi-tier Take Profit targets (TP1: 1.0x ATR for 50% lot scaling, TP2: 2.0x ATR for 30%, TP3: 3.5x ATR for 20%). Once TP1 is achieved, the Stop Loss is automatically shifted to Break-Even (+ spread buffer), eliminating downside risk on remaining position legs (`TPLadderManager`).

### 5. SHA-256 Cryptographic Audit Ledger
Every transaction step (`SIGNAL_GENERATED`, `SIGNAL_VETOED`, `ORDER_PROPOSED`, `ORDER_EXECUTED`) is recorded into a SQLite WAL mode ledger chained via SHA-256 hashes (`current_hash = SHA256(prev_hash | timestamp | event_type | payload)`). This satisfies Vault Rules P18 for tamper-evident chain of custody.
