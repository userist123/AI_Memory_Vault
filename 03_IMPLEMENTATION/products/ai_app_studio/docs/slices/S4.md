# S4 — Desktop UI ("see what the AI does")

## What
Tauri 2 + React 19 + TypeScript + Vite app in `apps/desktop` (DESIGN 5.5):

- Timeline: plan gate card, one row per step / tool call (current tool + target, +N/-M pills, durations),
  collapsed build log with auto-surfaced `file:line` errors, cost pill (tokens in/out, cost vs run budget),
  gap indicator, rejected-frame counter, `stream.dropped` warning, truncated `tool.result` sha256.
- Approval region (approvals and the plan gate card) fed only by `GET /api/v1/approvals` server records;
  `approval.*` and `plan.*` events only trigger a refetch (P6b). A `plan.proposed` event alone never renders a card.
- Approval/plan/tool fields fail closed: if sanitising would change a string (escapes, NUL, bidi, zero-width, tag
  chars, variation selectors, newline in a single-line field, truncation) the raw code points are shown as text
  (`\x1b`, `U+202E`), a warning is shown and Approve is disabled (Deny stays available).
- Live diff viewer (`agent.typing` while the model writes, `file.diff` when committed); when the followed target
  has no diff yet (e.g. `package.json` during `deps_install`) it falls back to the newest written file.
- Phone / tablet / desktop iframes of the preview origin `http://p-<id>.localhost:17880` with a tap overlay.
- Emulator mirror: WebCodecs decoder in a worker, fed by an H.264 Annex-B fixture.
- Follow the AI: focus moves to the panel of the latest event; pauses 10 s after any owner input.
- Demo mode `?demo=1[&speed=N]`: replays a fixture run, no backend, no network beyond its own origin.
- Strict CSP (tauri.conf.json); one Tauri command `get_session`, main window only, capability is exactly
  `allow-get-session` (no `core:default`).

## Contract consumed
Authoritative: DESIGN 5.4 and the real code on the backend branch (commit 39da19a45: `apps/backend/main.py`,
`core/studio_core/activity.py`).
- WS `ws://127.0.0.1:17875/api/v1/events?afterSeq=N`: `afterSeq` is a QUERY parameter of the upgrade URL
  (backend `events(ws, afterSeq: int = 0)`); the client sends nothing after open. Subprotocols offered
  `["aas.v1", "aas.token.<token>"]`; the server must echo exactly `aas.v1`. Any other negotiated value (token
  echoed, nothing) -> the client closes the socket, shows "refused socket" (token values are shown as
  `aas.token.<redacted>`) and retries with backoff.
- Frames `{seq, prev, kind, ts, runId, projectId, payload}`; `prev` is the seq last sent on that socket (for the
  first frame: `afterSeq`). Gap detection runs on EVERY frame including the first: `prev` missing or
  `prev != lastSeq` -> gap recorded, socket closed, reconnect with `afterSeq=lastSeq` (replay from the DB).
  Reconnect delay is at least 0.5 s, doubles up to 8 s and is reset only by an accepted frame, so repeated gaps
  cannot spin.
- `{type: "gap", after, before}` (row missing in the table): recorded as a gap after+1..before-1, no reconnect
  (the rows do not exist), not counted as a rejected frame.
- `projectId` is present in the frame (nullable on the backend). The UI is tolerant: an empty `projectId` keeps
  the project already known from earlier frames (preview host label); it never invents one.
- Frame size cap 64 KiB (`MAX_FRAME_CHARS`; backend payload JSON is capped at 8 KiB, envelope is small); larger
  frames are rejected before `JSON.parse` and counted.
- Kinds: allow-list in `src/lib/events.ts`; anything else is rejected and counted.
- `stream.dropped {count}`: items the server stream-json allow-list dropped (DESIGN 5.2). Summed and shown as a
  warning in the timeline; not a transport gap.
- `tool.result {callId, ok|isError, excerpt, size, sha256}`: sha256 kept only if 64-hex (lowercased), shown as
  the first 12 characters with the full value in the tooltip.
- REST (Bearer token): `GET /api/v1/approvals` returns pending records; records with `kind: "plan"` are plan-gate
  records `{id, kind: "plan", title, steps[], status}`, all others are approvals
  `{id, action|kind, argv[], target, reason, status}`. `POST /api/v1/approvals/<id>/decide` and
  `POST /api/v1/plans/<id>/decide`.

### Backend follow-ups (not present at 39da19a45, the UI is built to the DESIGN and mocked)
1. `main.py` has no `GET /api/v1/approvals`, no approval/plan decide routes and no plan records yet (DESIGN 5.5
   points at services.py). The plan gate uses `GET /api/v1/approvals` with `kind: "plan"` (one list, one
   refetch trigger); a dedicated `GET /api/v1/plans` would also work with a one-line change in `api.ts`.
2. Payload field names in `activity.py` differ from what the timeline reads: `step.started` has `text` (UI reads
   `title`), `tool.call`/`tool.result` have `operationId` and `input` (UI reads `callId` and `target`),
   `plan.proposed` has `planId, steps` only, `build.log` has `text` (UI reads `line`), `usage` replaces
   `cost.update`. Align one side before the first live run.
3. Gap frame `{type: "gap"}` carries no `kind`; handled client-side as above.

## Preview frame sandbox
`sandbox="allow-scripts allow-same-origin"` (DESIGN 4) is kept only because the preview origin
(`p-<id>.localhost:17880`) is never the app origin, so "same origin" grants the project's own origin, not the
studio's. Proven in `p3b_frame_ipc.spec.ts`: the frame cannot read `window.parent.document`, cannot reach the
Tauri IPC, cannot navigate the top window and its credentialed `fetch` to the API port never leaves the frame
(0 requests at the server). Positive controls: a frame sharing the app origin with the same sandbox tokens does
read the parent document; the identical probe served without the preview CSP and without sandbox does reach the
API.

### P3b honesty note
The iframe/IPC isolation proof runs in Playwright (Chromium) against the mock backend, with the same CSP and
sandbox tokens. It has NOT been run inside a real Tauri build: WebView2 treats `tauri://` / `*.localhost` frames
and IPC injection differently from Chromium, so "preview frames get no IPC" is verified by capability config
(the `default` capability is the single command `allow-get-session`, `windows: ["main"]`) plus the Chromium
probe, not by a probe inside the real WebView2. A local check against the debug build (run the exe with
`AAS_API_PORT`, load a preview page that probes `window.__TAURI_INTERNALS__` and `ipc.localhost`) is still to be
done by hand.
